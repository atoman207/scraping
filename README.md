# 転売リサーチツール — Next.js + Supabase 版

元の構成(Python + SQLite + Next.js)を、**Next.js + Supabase(PostgreSQL)だけ**で動くように
移植したものです。Pythonは不要になりました。

**元のコード(`../engine/`, `../scraper/`, `../webapp/`)は一切変更していません。**
このフォルダは丸ごと新規追加で、元の構成もそのまま並行して動きます。

## 何が変わって、何が変わっていないか

| | 元 | このフォルダ |
|---|---|---|
| 画面(UI) | Next.js 3画面 | **同一**(JSX・スタイル・文言をそのままコピー) |
| 利益計算式 | `webapp/lib/db.ts` / `engine/profit_calc.py` | **同一**(`lib/db.ts` に一字一句そのまま) |
| 鉄板商品の抽出 | `engine/cluster_seller_listings.py` | `lib/engine/cluster.ts`(同一アルゴリズムをTS移植) |
| セラー集計 | `engine/rank_sellers.py` | `lib/engine/rank.ts` |
| CSV取り込み | `scraper/import_csv.py` | `scripts/import-csv.ts` |
| DB | SQLite(`data/tenbai.db`) | **Supabase(PostgreSQL)** |
| Basic認証 | `webapp/middleware.ts` | **同一**(そのままコピー) |
| スクレイパー | 型定義のみ(未実装) | **Playwrightで実装**(3-1/3-2/3-3) |

UIは1文字も変えていないので、画面上の説明文には元のPythonコマンド名
(`engine/rank_sellers.py` など)がそのまま出ます。実際に叩くコマンドは下記の
`npm run engine:*` に置き換わっています。

Pythonの `difflib.SequenceMatcher`(タイトル類似度の計算に使っている)は、
CPythonのアルゴリズムをそのまま `lib/engine/difflib.ts` に移植しています。
同じタイトル群に対してPython版と同じグルーピング結果になります。

## セットアップ

### 0. 必要なもの
- Node.js 18以上(動作確認は v24.17.0)
- Supabaseのアカウント(無料枠でOK) https://supabase.com/

### 1. Supabaseプロジェクトを作る
Supabaseにログイン → New project → リージョンは `Northeast Asia (Tokyo)` あたりを選択。
作成後、**Project Settings > API** で以下2つを控えます。

- `Project URL`(`https://xxxx.supabase.co`)
- `service_role` の `secret` キー(**ブラウザに出してはいけない鍵です**)

### 2. 環境変数を設定する
**`.env.local` は作成済みです**(いただいた URL / secret キーを設定済み)。
新しく作り直す場合は:
```bash
cd tenbai-next
cp .env.example .env.local
```
`.env.local` を開いて `NEXT_PUBLIC_SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` を
1で控えた値に書き換えます。友人に配る場合は `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` も設定してください
(未設定なら認証なしで動きます。元の webapp と同じ挙動)。

### 3. テーブルを作る
**すでに適用済みです**(いただいたSupabaseプロジェクトに対して確認済み)。
新しいプロジェクトを作り直すときだけ、以下のどちらか一方を実行してください。

**方法A(推奨・手軽)**: Supabaseダッシュボードの **SQL Editor** に
`supabase/schema.sql` の中身を貼り付けて Run。

**方法B(コマンド)**: `.env.local` に `DATABASE_URL`
(Project Settings > Database > Connection string の URI)を設定してから:
```bash
npm install
npm run db:push
```

`schema.sql` は何度実行しても壊れない(冪等)ので、作り直しのときもそのまま流せます。

### 4. 起動する
```bash
npm install
npm run build
npm run start      # 開発中は npm run dev でも可
```
http://localhost:3000

同じLAN内の別の端末（ノートPC・スマホ）からは `http://<このPCのIPアドレス>:3000` で開けます。
待ち受けは最初から全アダプター（`-H 0.0.0.0`）なので、初回に Windows のファイアウォールを
開けるだけです — `ops/allow-lan-access.cmd` を「管理者として実行」。
手順は **DEPLOY.md「3-2. 他の端末のブラウザから開く」** にまとめてあります。

開けないときは `ops/lan-doctor.cmd` を実行してください。原因（画面が落ちている／
ファイアウォールの許可範囲が狭い／通信がそもそも届いていない）を切り分けて表示します。

初回は**ログイン画面**が出ます。既定の管理者アカウントは固定で、
画面には表示されません(値は「管理者アカウント」の節を参照)。
公開サーバーに置く場合は `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` を必ず設定してください。

- `/login` — ログイン
- `/` — ① セラーリサーチ結果(直近の検索の集計値)

## ログインと会員管理

**利用者は自分で登録できません。** ログインIDとパスワードは管理者が `/admin` で発行し、
本人に渡す運用です。

### しくみ

| | |
|---|---|
| パスワードの保存 | 平文では持たず、`node:crypto` の **scrypt** でハッシュ化(利用者ごとに塩を変える) |
| ログイン状態 | DBのセッション(`app_sessions`)。ブラウザのCookieには token だけ(httpOnly・SameSite=Lax・本番はSecure) |
| 有効期間 | 30日。期限切れはログイン画面を開いたときに掃除されます |
| 認可の確認場所 | `app/(app)/layout.tsx`(全画面)・各APIの入口・各サーバーアクションの先頭 |

middleware は **Cookieがあるかどうかしか見ていません**(Edgeランタイムで動くため)。
本当の検証は上記のサーバー側で毎回行うので、偽のCookieを付けても中身は見られません。

### 管理者アカウント

既定の管理者アカウントは **固定** です(`lib/auth.ts` の `FIXED_ADMIN_USERNAME` / `FIXED_ADMIN_PASSWORD`)。

- ログイン画面や管理画面を開いたときに、いなければ自動で作られます
- パスワード・権限・有効状態の変更、削除は **できません**(画面にもその操作は出ません)
- DBを直接書き換えられても、次にログイン画面を開いた時点で既定値に戻ります
- 環境変数(`ADMIN_USERNAME` / `ADMIN_PASSWORD`)は参照しません
- 資格情報はログイン画面には表示しません
- 固定の資格情報なので、**公開サーバーに置く場合は `BASIC_AUTH_USER` / `BASIC_AUTH_PASS`(手前のBasic認証)を必ず設定してください**

### /admin でできること

| 操作 | 説明 |
|---|---|
| **ランダムに発行** | ログインIDとパスワードを自動生成して利用者を作る。紛らわしい文字(0とO、1とl)は使わない |
| **指定して発行** | ログインIDとパスワードを自分で決めて作る |
| **編集** | 表示名・メモ・権限(管理者/一般)・有効/停止 |
| **パスワード再発行** | 新しいランダムなパスワードを発行(古いパスワードとログイン状態は無効になる) |
| **ログイン解除** | その利用者のログイン状態だけを全部切る |
| **削除** | 利用者を削除(セッションも一緒に消える) |

発行したパスワードは**その場で1回しか表示できません**(ハッシュしか保存しないため)。
画面にコピーボタンがあるので、その場で控えて本人に渡してください。

安全のための制限:

- 管理者が1人もいなくなる操作(最後の管理者の削除・降格・停止)はできません
- 自分自身は削除できません
- 既定の管理者は変更・削除できません(表示名とメモだけ編集できます)
- 既定の管理者と同じログインID(大小文字違いを含む)は発行できません
- 停止・削除・パスワード再発行を行うと、その利用者のログインはその場で無効になります
- ログイン失敗時に「IDが違う」「パスワードが違う」を区別しません(存在するIDの特定を防ぐため)

```bash
npm run test:auth   # ハッシュ化・資格情報の生成・入力チェックを検証(DB不要)
```

### Basic認証(任意)

`BASIC_AUTH_USER` / `BASIC_AUTH_PASS` を設定すると、ログイン画面の**手前**に
もう1枚Basic認証をかけられます(公開サーバーに置くときの二重の壁)。未設定なら何もしません。

## スクレイパー(発注仕様書 3-1 / 3-2 / 3-3)

Playwright(Chromium)で **ログイン不要の公開ページ** を実ブラウザで開いて読みます。
非公開の内部APIやトークンには触れていません。

> **初回は、ブラウザ本体のダウンロードが要ります**（`npm install` では入りません）。
> `ops/install-browser.cmd` をダブルクリック、または `npx playwright install chromium`。
> 入っていないと、リサーチの実行直後に
> `browserType.launch: Executable doesn't exist at ...` で止まります。
> `npm run test:browser` で、メルカリに触らずに起動できるかだけ確認できます。

読み方は2段構えです。まず **ページ自身が描画のために受け取ったレスポンス** を読み、
それが読めなかったときだけ **レンダリング後のDOM** を読みます。
前者はこちらから叩くのではなく「ページを開いた結果として届いたもの」を読むだけなので
アクセス回数は増えず、しかもDOMには出ない項目(出品者ID・出品日時・配送方法・実送料)が取れます。

|---|---|---|

**画面(`/api/scrape`)・ジョブキュー(`/api/jobs` + `npm run worker`)・CLI のどこから実行しても同じ結果**になります。

### 実行の経路は2つあります

| | 画面の実行パネル(`/api/scrape`) | ジョブキュー(`/api/jobs` + ワーカー) |
|---|---|---|
| 実行する場所 | 画面を動かしているサーバー自身 | 常駐ワーカー(別プロセス。VPSや手元のPC) |
| 進捗とログ | メモリ上のみ(再起動で消える) | `jobs` テーブルに残る |
| サーバーレス(Vercel等) | 使えない(Playwrightが動かない) | 使える(画面はDBに1行入れるだけ) |
| 対応 | 3-1 / 3-2 / 3-3 | 3-1 / 3-2 / 3-3 |

いまの画面のボタンは前者を使っています。後者は `curl` かワーカー運用から使う想定で、
使い方は [DEPLOY.md](./DEPLOY.md) の「動作確認」にまとめています。

### 画面から実行する
①②③の各画面に実行パネルがあり、押すとバックグラウンドで走ります。
実行中は **段階表示(いま何をしているか)・進捗バー・経過時間・ログ** が出ます。
進捗はサーバーが返す実際の値(`lib/jobs.ts` の `JobProgress`)に基づいていて、見た目だけの演出ではありません。

- ① セラーリサーチ: キーワード/あるあるワード/ページ数/出品者を調べる件数 を入れて「メルカリを検索」
- ② セラー深掘り: 「このセラーの出品を再取得」(標準=上位3件 / 詳細=上位20件 の実送料取得を選べます)
- ③ 深掘りリスト: 「仕入れ候補を探す」(タイトル検索・画像検索を選べます。候補は行の上に並び、「採用」で単価と仕入先URLが入ります)

画面には**セラーのプロフィール画像**を出します。

通常セラーの画像URLは **セラーIDから一意に決まる**ため
(`https://static.mercdn.net/thumb/members/webp/<セラーID>.jpg`)、
プロフィールを取りに行っていないセラーでも画像が出ます。
スクレイプ時に取得できた場合はその値を優先します(メルカリShopsの店舗ロゴはIDから
決まらないので、この経路でしか出せません)。
画像を設定していないセラーはこのURLが403を返すので、名前の頭文字を色付きの丸にして
見分けられるようにしています。

### 3-3 仕入れ候補(AliExpress / 1688)

鉄板商品(`product_groups`)の**タイトルと画像**から、AliExpressで類似商品を探して
深掘りリストの各行に候補として並べます。

| | タイトル検索 | 画像検索 |
|---|---|---|
| 何をするか | タイトルから検索語を作って `/w/wholesale-〜.html` を開く | 商品画像を検索窓のカメラからアップロードする |
| 使う画像 | — | **同じ出品の写真を最大3枚**(既定。`imageCount` で変更) |
| 得意なこと | 名前で言い表せる商品 | **名前は違うが見た目が同じ**商品 |
| 弱いこと | 中国語圏では別の名前で売られている商品 | 形が似ているだけの別商品を拾うことがある |

どちらの探し方で見つけた候補かは画面に出るので、混ざって分からなくなることはありません。

**検索語の作り方**: タイトルから「新品」「送料無料」「★」などの売り文句と記号を落とし、
長い語を優先して4語まで採用します(`toSearchQuery()`)。
実際に投げた検索語は候補の上に出るので、狙いとずれていれば手で調べ直せます。

**画像検索が写真を複数枚使う理由**: メルカリの1枚目は文字入れ・箱・複数点を並べた写真の
ことが多く、画像検索にいちばん向いていません。2枚目以降は商品そのものを素直に写している
ことが多いので、`mercariPhotoUrls()` で `m<商品ID>_1..N.jpg` を組み立てて順に検索します
(写真が少ない出品では存在しない番号が403を返すので、その枚は黙って飛ばします)。
結果は商品IDで突き合わせ、**複数の写真から出てきた商品を先頭**に、
同数ならAliExpressが返した順(=見た目の近い順)で並べます。

**一致度**: 元のタイトルと候補タイトルの近さを0〜100%で出します。
検索語の単語がいくつ含まれるか(65%)と、文字列としての近さ(35%)の合成です。
**目安であって保証ではありません。** 発注前に必ず現物の写真とサイズを確認してください。

**一致度は「タイトル検索」にしか使いません。** 画像検索は「名前は違うが見た目が同じ」商品を
拾うのが値打ちなので、一致度が低いことは候補が悪いことを意味しません。むしろ良い候補ほど
低い数字になり、画面に出すと使える候補が悪く見えてしまいます。そのため
**画像検索の候補には一致度を表示せず、並べ替えにも使いません**(`rankCandidates()` は
探し方ごとに別々に並べ、画像検索は `source_rank` の順を守ります)。

**価格**: AliExpressの日本向け表示は円なので、共通設定の為替(円/元)で元に換算し、
そのまま `deepdive_items.unit_cost_cny` に入れられる形にしています。
AliExpressは検索結果・商品ページ・新規向けクーポンで**表示価格が変わる**ので、
候補の価格は「そのときの検索結果の表示」です。発注前に商品ページで確認してください。

**深掘りリストへの反映**:

- 「仕入れ候補を探す」ボタン … 単価が**未入力の行にだけ**最有力候補を入れます
  (手で調べて入れた値を、自動検索が黙って書き換えないため)
- 候補の「採用」ボタン … その候補の単価と仕入先URLで**上書き**します(利用者が選んだ操作なので)

最有力候補は次の順に選びます(`pickBest()`)。自動で原価に入る値なので、
確かめようのない画像検索の結果は最後の手段にしています。

1. **タイトル検索**で一致度40%以上 → その中でいちばん安いもの
2. 1が無ければ、タイトル検索の上位5件から安いもの
3. タイトル検索が空のときだけ、**画像検索の上位3件**から安いもの

**1688 について**: **すべての経路がログイン必須**です。2026-09 時点で実機確認済み
(実Chrome・日本語ロケール・`navigator.webdriver` を隠した状態でも同じ)。

| 経路 | 未ログインでの結果 |
|---|---|
| `detail.1688.com/offer/…` | `login.taobao.com` へリダイレクト |
| `s.1688.com/selloffer/offer_search.htm` | `login.taobao.com` へリダイレクト |
| `s.1688.com/youyuan/…?tab=imageSearch` | スライダーCAPTCHA(`验证码拦截`) |

ヘッドレス判定の問題ではなく、認証済みセッションが要るということです。
ログインの偽装もCAPTCHAの自動突破もしない方針なので、
**人が開けばそのまま使える検索URLを組み立てて出す**だけにしています。

### 1688 から商品を取る — 1688Japan(公式総代理店)経由 ★本命

1688.com を直接読むことはできませんが、**1688Japan**(アリババ1688の日本唯一の公式総代理店)
の会員ページから、1688の商品を正規に検索できます。検索画面にも
「こちらの検索は、1688より一部技術、情報サポートを受けて提供させて頂いております」と明記されています。

**ブラウザは使いません。** 認証はCookieの `token` ひとつで通るため、HTTPだけで完結します。

```
1. GET  /oss/upload-ticket?type=image-search   署名付きアップロード先をもらう
2. POST <OSSのhost>                             写真をそこへ置く
3. POST /goods/image-search                     置いた写真のURLで検索  → 最大50件
```

キーワード検索は `POST /goods/search` の1回だけです(中国語で投げる)。
実装は [`lib/scraper/sourcing-1688jp.ts`](./lib/scraper/sourcing-1688jp.ts)。

**受け取れる情報**(AliExpress には無いものが多い)

| 項目 | 例 |
|---|---|
| タイトル | **日本語に翻訳済み**(1688の原文は中国語) |
| 価格 | `4.28` 元(卸売価格。共通設定の為替で円にも直す) |
| 月間販売数 | 1376 |
| リピート率(回头率) | 20.83% |
| 取引スコア | 4.9 |
| 最小ロット | 1 |
| 店のバッジ | 実力商家 / 厳選工場 / 誠信通 / 1688厳選 |

**価格の違い**(実測・同じチェーンロック)

| | 価格帯 |
|---|---|
| AliExpress(小売) | ¥171〜3,321 |
| **1688(卸売)** | **¥69〜371** |

同じ商品でも桁が1つ違うため、原価計算に使うのは1688です。
`pickBest()` も 1688 を優先します(1688の画像検索で複数の写真から一致 → 上位3件 →
1688のキーワード検索 → AliExpress、の順)。

**ログインについて**

ログイン画面に画像の確認コードがあるので自動ではログインしません。
人が1回ログインして、そのセッションを預かります。

```bash
npm run login:1688jp     # ブラウザの窓が開くので、画面でログインする
npm run test:1688jp      # セッションが生きているか確認(切れたら login し直す)
```

セッションは `secrets/` に置きます(`.gitignore` 済み)。**中身はログイン情報そのもの**なので、
コミットしたり人に渡したりしないでください。置き場所は `SOURCING_1688JP_STATE` で変えられます。

**セッションを切らさない工夫**

Cookie には「30日」と書かれていますが、それは**ブラウザがその Cookie を捨てる日**です。
こちらはブラウザを使わず、ファイルから読んだ `token` をヘッダーに載せて送るので、
その日付そのものが動作を止めるわけではありません。止まるとしたら相手が鍵を無効にしたときで、
それがいつかは外からは分かりません。そこで3つで備えています。

| | |
|---|---|
| **毎日1回の生存確認** | 常駐ワーカーが1日1回 `getUserInfo` を通します(1リクエストだけ)。相手が「使うたびに期限を延ばす」作りならこれで期限が来ません |
| **早めの警告** | 最後に通った日時を記録し、残り7日を切ったら③の画面とワーカーのログに出します。黙って切れることはありません |
| **入り直しを数十秒に** | `.env.local` に `SOURCING_1688JP_USER` / `_PASS` を入れておくと、`npm run login:1688jp` がID/パスワードを自動で埋めます。人が打つのは**画像の確認コード4桁だけ**です |

ワーカーを動かしていない構成では、タスクスケジューラで1日1回これを叩いてください。

```bash
npm run keepalive:1688jp   # 通れば終了コード0、切れていたら1(監視ツールから叩ける)
```

画像の確認コードの自動突破はしません。相手が人の操作を求めている以上そこは人がやる、
という方針は他のスクレイパーと同じです。その代わり、**突然切れて困らない**ようにしてあります。

セッションが切れている場合は、1688 の候補だけを諦めて
「人が開けば使える検索リンク」に切り替えます(AliExpress の結果は捨てません)。

**1688のキーワードは中国語に直します**(`lib/scraper/zh-query.ts`)。1688は中国国内向けの
卸売サイトで商品名はすべて簡体字なので、日本語のまま投げると0件になります。
外部の翻訳APIに依存せず、中国輸入で頻出する語を収めた対訳表(`JA_ZH`)で置き換えます。

- 長い語から照合するので、「スマホスタンド」のような複合語が優先されます
- 採用は4語まで(多すぎると1688側で0件になる)。どれを残すかは**元の語が長い順**
- 並びは**元のタイトルの語順**に戻します(「ペット ハーネス」→「宠物 胸背带」)
- 対訳表で1語も訳せなかったときだけ漢字語をそのまま使い、画面のラベルに
  **「自動訳・要確認」**と出します(日本語の新字体と簡体字は別字なので当たらないことがある)

語彙を足すには `JA_ZH` に1行足すだけです。訳せ具合は次で確認できます。

```bash
npm run test:zh            # 例題だけ(ネットワーク不要・DB不要)
npm run test:zh -- --db    # いまDBにある商品タイトルでの訳せ具合と、訳せなかった語の一覧
```

候補は `sourcing_candidates` テーブルに保存され、同じ商品を検索し直すと入れ替わります
(採用の印は同じURLの候補が再び見つかれば引き継ぎます)。

### アクセスの作法
- ページ遷移は必ず **2.5秒以上の間隔 + ランダムなゆらぎ** を空け、並列アクセスはしません
- 画像・フォント・広告/計測タグは読み込まずに中断(転送量とサイト側の負荷を下げるため)
- HTTP 403/429/503 やブロックページを検出したら **その場で停止** します(`BlockedError`)。
  自動でリトライして回り込むようなことはしません。止まったら `--interval` を広げて時間をおいてください
- 取得するのは公開されている出品情報だけで、個人情報は取得していません

### 既知の制限(重要)
- **売却日時(`sold_at`)は取得できません。** メルカリの公開ページに売却日時が出ないためです。
  代わりに最終更新日時(`updated_at`)を売却時刻の目安として保存し、
  **回転日数は「出品日時 → 最終更新日時」で推定**しています。
- **実送料は「発送された商品」でだけ取れます。** 発送時に確定したサイズ区分と金額
  (ネコポス210円、ゆうパケットポストmini160円 など)を商品ページから読みます。
  普通郵便・定形外・レターパック・ゆうメールなどメルカリが配送を担当しないもの、
  発送方法未定、まだ発送されていないもの、メルカリShopsは仕様書どおり取得不可(null)です。
  「取れなかった」と「そもそも対象外」は `listings.ship_status`
  (`got`/`fixed`/`failed`/`na`/`skip`)で区別して保存します。詳細は [TEST_3-2.md](./TEST_3-2.md)。
- **商品の状態(新品/中古)はセラーページの出品一覧に含まれません。** 深掘りで取った出品の
  `is_new` は `NULL` になります(実送料を取りに行った上位N件だけは取得できます)。
- **メルカリShopsは売り切れと在庫切れを区別できません。** 在庫の有無しか公開されていないためです。
- **ブロックされたら止まります。** 通常のChromeとして名乗る・アクセス間隔を空けるといった
  「弾かれる原因を取り除く」対策はしていますが、CAPTCHAの自動突破・プロキシ切り替え・
  ブラウザ指紋の偽装・**断られた後の再挑戦**は実装していません。
  HTTP 403/429/503 を受け取った時点で `BlockedError` で停止します（[TEST_3-2.md](./TEST_3-2.md) 参照）。
- **出品者「名」は検索結果に含まれていません。** IDは全件分かりますが、名前はプロフィールページを
  1人ずつ開く必要があり、1人あたり約3秒かかります。そのため `--resolve`(既定30人)で
  「集計して上位N人だけ名前を引く」設計にしています。
- **メルカリShops** の商品(IDが `m` + 数字でないもの)は `/shops/product/...` にあり、
  出品者は `shops:<ショップID>` として区別して保存します。
- **AliExpressの価格は表示のたびに変わります。** 検索結果・商品ページ・新規向けクーポンで
  違う金額が出るため、候補に出る価格は「そのときの検索結果の表示」です。発注前に商品ページで確認してください。
- **一致度(%)は目安です。** タイトルの重なりから機械的に出した数字で、同じ商品であることの保証ではありません。
  画像検索は「見た目が似ているだけの別商品」を拾うこともあります。必ず写真とサイズを目で確かめてください。
- **AliExpressの画像検索は、画面の作りに依存します。** 検索窓のカメラにマウスを乗せて現れる
  ファイル入力に画像を渡す方式なので、この部分が変わると画像検索だけ0件になります
  (そのときもタイトル検索の結果はそのまま使えます。ログに理由が出ます)。
- **1688 は検索ページがログイン必須** で、未ログインだと `login.taobao.com` にリダイレクトされます。
  ログインを突破する実装は入れていないため、検索リンクの生成だけにとどめています。
  自動化したい場合はアカウントを用意して認証済みのブラウザプロファイルを使う必要があります。
- **サイト構造が変われば壊れます。** セレクタは `lib/scraper/mercari.ts` 冒頭のコメントに
  まとめてあるので、壊れたときはそこを見てください。取得0件のときは黙って成功扱いにせずログに出します。
- **Playwrightは常駐サーバーでしか動きません。** Vercel等のサーバーレスにデプロイした場合、
  画面の実行パネル(`/api/scrape`)は使えません。その場合は **ジョブキュー経由**
  (`/api/jobs` にジョブを積み、常駐マシンの `npm run worker` が実行する)か、
  CLIを常駐マシンで回してSupabaseを共有する構成にしてください。
  ジョブキューは 3-1 / 3-2 / 3-3 のすべてを受け付けます。
- 画面の実行パネル(`/api/scrape`)の進捗ログは **メモリ上のみ** に保持します
  (サーバー再起動で消えます)。ジョブキュー(`/api/jobs` + ワーカー)経由なら
  進捗もログも `jobs` テーブルに残ります。どちらの経路でも取得結果はSupabaseに入るので失われません。

### 利用規約について
メルカリの利用規約は自動化されたアクセスを認めていません。発注仕様書にも
「規約解釈や実施可否の最終判断は発注者側で行う」とある通り、実運用の判断はご自身でお願いします。
技術者としての所見としては、(a) 公開ページのみ・低頻度・個人情報を取らない、という条件でも

## デプロイ(Vercel)

**画面(①②③の閲覧・原価入力・利益計算)はVercelで問題なく動きます。**
**スクレイピングだけはVercelでは動きません。** ヘッドレスブラウザ(Chromium)を
サーバーレス環境で起動できないためです。役割を分けて使ってください。

| 機能 | Vercel | 常駐サーバー(PC / VPS) |
|---|---|---|
| ①②③の画面表示・原価入力・利益計算 | ○ | ○ |
| 画面のスクレイパー実行ボタン | ×(理由を表示して無効化) | ○ |
| `npm run scrape:*` コマンド | × | ○ |

どちらも同じSupabaseを見るので、**手元でスクレイピングして、結果をVercelの画面で見る**
という使い方ができます。友人に共有するのはVercelのURLだけで済みます。

### 設定手順

1. このフォルダをGitHubにpush
2. Vercelで Import → **Root Directory に `tenbai-next` を指定**(ここを忘れると
   リポジトリ直下を見に行ってビルドが失敗します)
3. Environment Variables に以下を設定

   | 変数 | 値 |
   |---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | SupabaseのProject URL |
   | `SUPABASE_SERVICE_ROLE_KEY` | Supabaseのsecretキー |
   | `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` | `1` |
   | `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` | 共有相手用のID/パスワード(任意) |

   `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` は、ビルド時に約150MBのChromiumを
   ダウンロードしないようにするためのものです。どうせ起動できないので、
   付けておくとビルドが速くなります。
4. Deploy

### Vercel向けに入れてある対策

- `app/api/scrape/route.ts` の `maxDuration` は **60秒**。
  Vercelはプランごとに上限(Hobby=60秒 / Pro=300秒)があり、これを超える値を
  書くとデプロイが失敗します。スクレイピング本体はレスポンスを待たせずに
  バックグラウンドで走るので、ハンドラ自体は短くて問題ありません。
- `lib/scraper/browser.ts` は playwright を **動的import** しています。
  Chromiumが無い環境でもビルドと起動が通ります。
- `next.config.js` の `outputFileTracingExcludes` で playwright を
  サーバーレス関数のバンドルから除外しています(関数サイズの上限対策)。
- `lib/scraper/environment.ts` が実行環境を判定し、Vercel上では
  画面に理由を表示してボタンを無効化します。APIも503と説明文を返します。
  「押したのに無言で失敗する」ことはありません。

### 常時スクレイピングしたい場合

VPS(さくらVPS、ConoHa、Hetznerなど)か自宅PCで `npm run build && npm run start` を
動かせば、画面の実行ボタンもそのまま使えます。Dockerで動かす場合は

## セキュリティについて

- DBアクセスは全て**サーバー側**(Server Component / Server Action / CLIスクリプト)からのみ。

## 既知の制限・注意点

- スクレイパーは実装済みです(「スクレイパー」の節を参照)。CSV取り込み(`npm run import:csv`)も併用できます。
- ①セラーリサーチ画面には検索フォームを追加し、スクレイパーに接続済みです。
- `new_item_rate`(新品率)は元のPythonコードと同じくプレースホルダ(NULL)です。
  `listings` に `condition` カラムを足すのが本来の実装です。
- 日付カラムは元のSQLite版と同じ `text` 型のままにしています(`YYYY-MM-DD` 形式)。
  回転日数は SQLite の `julianday()` 差分と同じ計算をTS側で行っています。
- ③深掘りリストの並び順は `deepdive_id` 昇順を明示しています(SQLiteでは登録順で
  返っていたものを、PostgreSQLで同じ見え方にするため)。
- 数値の丸めは元の `webapp/lib/db.ts` と同じ `Math.round`(四捨五入)です。
  Pythonの `round()`(偶数丸め)とは `.5` ちょうどのときだけ差が出ます。

## ルートの `../schema.sql` について

作業中に、ルートの `../schema.sql` がSQLite版からPostgreSQL版に書き換えられていました
(私の変更ではありません)。**このSupabaseプロジェクトには既にそちらが適用済み**で、
アプリはその状態でそのまま動くように作ってあります(①のJOINはビューではなく
PostgRESTのリソース埋め込みで行っているため、追加のDDLは不要です)。

ただし2点だけ差があります。作り直す機会があれば `supabase/schema.sql` のほうを推奨します。

- **数値の精度**: ルート版は `REAL`(PostgreSQLでは4バイト float)です。SQLiteの `REAL` は
  8バイトなので、元と厳密に同じにするなら `double precision` が正しい対応です
  (`supabase/schema.sql` はそちら)。実害としては平均価格などが有効数字7桁に丸められます
  (例: 1976.6666666666667 → 1976.67)。今回の利益計算では表示結果に差は出ませんでした。
- **日時形式**: ルート版の `NOW()::TEXT` はマイクロ秒+タイムゾーン付き
  (`2026-08-29 16:37:51.976708+00`)になります。SQLiteの `datetime(now)` は
  `YYYY-MM-DD HH:MM:SS` 形式です。`created_at`/`fetched_at` は表示に使っていないので実害はありません。
